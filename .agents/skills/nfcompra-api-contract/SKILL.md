# NFCompra API Contract (`/v1`)

Rules for changing the NFCompra Cloudflare Worker + D1 backend and the shared contract.

## When to load
- Adding or changing `/v1` routes, request/response shapes, or error codes.
- D1 migrations, catalog seeds, or user-data deletion.
- Auth/session/OTP/cookie changes.

## Architecture facts
- `apps/api/src/index.ts` uses a **custom router** (manual URL matching + `isShoppingRoute`/`isCatalogRoute`), not Hono. Follow that pattern.
- Auth is the Worker's job: every protected route re-checks membership/role server-side. Never rely on the client hiding UI.
- Auth model: access token = custom HMAC-SHA256 JWT (1h) signed with `JWT_SECRET`; refresh token = random token stored **hashed** in D1, delivered as `HttpOnly; Secure; SameSite=Lax` cookie (web) or in body (Android). Tokens for email verify / password reset / invitations are stored hashed, single-use, with expiry (30 min for recovery, 7 days for invitations).
- Email goes through `ResendEmailSender` (fake sender in tests). Never hardcode email keys.

## D1 rules
- Migrations are forward-only SQL files in `apps/api/migrations/`, applied with `npx wrangler d1 migrations apply DB --local` or `--remote`.
- No cascade deletes that orphan rows; user deletion requires manual cleanup (see `docs/user-deletion-d1.md`).
- Atomicity matters: invitation accept, member add, and notification triggers belong in the same batch/transaction.
- Catalog SQL seeds are generated by `npm run catalog:build-sql`; use the existing seed JSONs and `--no-transaction` for remote D1.

## Contract change checklist
1. Update `apps/api` route(s) + migration if schema changes.
2. Update `docs/api-contract.md`.
3. Update PWA client (`apps/web`) and Android (`apps/android`) in the same delivery — all three share `/v1`.
4. Run API validation:
   `npm run api:test && npx --workspace @nfcompra/api tsc --noEmit`

## Gotchas
- Errors use the envelope `{ "error": { "code", "message", "details" } }`.
- CORS: `ALLOWED_ORIGINS` in wrangler config controls origins; `OPTIONS` preflight is handled in `createWorker`.
- Operation idempotency: a completed `operationId` replays its response; pending one returns `409 OPERATION_IN_PROGRESS` (Android sync relies on this).
